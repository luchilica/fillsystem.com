# 06. Производительность, доступность, безопасность, юридические страницы

## 6.1. Аналитики нет — при работающем баннере согласия

В бандле:

```js
e.s(["ANALYTICS_ENABLED", 0, !1,  ...  "CONSENT_UI_ENABLED", 0, !0, ...])
let o = process.env.NEXT_PUBLIC_GA4_MEASUREMENT_ID || ""
function i() { return a.ANALYTICS_ENABLED && "" !== o && !r.isPreview && hasAnalyticsConsent() }
```

`ANALYTICS_ENABLED = false` (литерал `!1`, зашит в сборку), ID GA4 — пустая строка. Функция `isAnalyticsReady()` не может вернуть `true` ни при каком согласии.

В бандл при этом входит и остаётся мёртвым кодом:
- загрузчик GA4 (`loadGA4` / `unloadGA4`),
- `trackEvent` с фильтрацией PII (`email, name, company, challenge, phone, password`),
- глобальный делегированный слушатель кликов по CTA (`#diagnostic-request-form`, `#how-the-diagnostic-works`),
- вся логика согласия и её событийная шина.

Одновременно `CONSENT_UI_ENABLED = true` — баннер и «Cookie Preferences» в футере работают. Сайт спрашивает разрешение на аналитику, которой не существует.

Никакого другого счётчика тоже нет: ни GTM, ни Vercel Analytics, ни Clarity, ни Plausible, ни LinkedIn Insight Tag, ни Meta Pixel. Проверено по всем 14 JS-чанкам и по SSR-HTML.

**Что это значит на практике:** неизвестно ничего. Сколько людей доходит до формы, где отваливаются, какая локаль даёт трафик, работает ли слайдер цен, читают ли блог, откуда приходят. Все решения по сайту принимаются вслепую.

**Что делать сегодня:** задать `NEXT_PUBLIC_GA4_MEASUREMENT_ID`, включить `ANALYTICS_ENABLED`, поднять GA4 с событиями `form_start`, `form_submit`, `cta_click`, `price_slider_change`, `service_detail_view`. Добавить Vercel Analytics (Web Vitals из реальных сессий) и Google Search Console. Если аналитику включать не планируют — убрать баннер согласия и мёртвый код из бандла.

## 6.2. Русский и китайский текст грузятся на английской главной

Один чанк — `10r-frwl-wwi3.js` — весит **860 101 байт** несжато / **269 614 байт** по сети. Внутри:

| Содержимое | Объём |
|---|---|
| Кириллические символы | **204 281** (~400 KB в UTF-8) |
| Иероглифы CJK | 9 664 |
| Испанские диакритики | 830 |

Это словари всех четырёх локалей, включая **полные переводы тел статей блога** (в бандле лежат целые абзацы вроде перевода RevOps-гайда на русский). Они не разделены по code-split и грузятся на каждой странице каждой локали.

То есть посетитель английской главной скачивает ~400 KB русского текста, который никогда не увидит.

**Общая картина по главной:**

| Ресурс | По сети (br/gzip) | Несжато |
|---|---|---|
| HTML | 30 KB | 244 KB |
| JS, 13 чанков (без legacy-полифилла) | **~464 KB** | **~1,51 MB** |
| JS legacy-полифилл (`noModule`) | 41 KB | 113 KB |
| CSS, 3 файла | 19 KB | — |
| Шрифты, 2 × woff2 | 61 KB | — |
| LCP-изображение (AVIF, 1080–1920px) | 95–124 KB | — |
| **Итого первая загрузка** | **≈670–700 KB** | |

Для маркетингового лендинга без интерактива, кроме одного слайдера и формы, ~1,5 MB JS — это в 3–4 раза больше нужного.

**Что делать:**
1. Разнести словари локалей по чанкам (`next-intl` / динамический `import()` по локали). Ожидаемая экономия на EN-странице: ~400–450 KB несжато, ~120–150 KB по сети.
2. Не класть переводы тел статей в клиентский бандл вообще — они нужны только при SSR.
3. Отключить legacy-полифилл, если браузерная матрица позволяет (−113 KB).

## 6.3. LCP-изображение не приоритизировано

```html
<link rel="preload" as="image"
      imageSrcSet="/_next/image?url=%2Fphotos%2Fproblem.jpg&w=640&q=75 640w, … 3840w"
      imageSizes="(min-width: 1200px) 1200px, 100vw" />
```

Preload есть — это хорошо. Но:

- **атрибута `fetchpriority="high"` нет.** Единственное вхождение `fetchPriority` во всём HTML — это `fetchPriority="low"` у скрипта. То есть LCP-картинка конкурирует за полосу с 13 JS-чанками на равных;
- в `srcset` присутствуют варианты до `3840w` (185 KB), хотя `sizes` ограничивает отображение 1200px — лишние строки в srcset безвредны, но говорят о том, что `sizes`/`quality` не подбирали;
- исходники в `/photos/` и `/services/` — JPEG по 200–212 KB, `q=75` по умолчанию. При таком весе оригиналов AVIF-версия 1080px выходит на 95 KB, что для фонового фото много.

**Что делать:** `priority` на `next/image` для героя (даст `fetchpriority="high"`), пережать исходники до ~1600px по длинной стороне, снизить `quality` до 65 для декоративных фото.

## 6.4. Шрифты

Два webfont-семейства, 2 × ~30 KB, оба с `preload`:
- **Mulish** — основной текст,
- **JetBrains Mono** — акцентные подписи.

`font-display: swap` выставлен — корректно. Fallback-метрики сгенерированы (`Mulish Fallback`, `JetBrains Mono Fallback`) — Next.js делает это правильно, CLS должен быть низким.

Замечания:
- 30 KB моноширинного шрифта ради нескольких цифровых акцентов — сомнительная цена;
- оба шрифта грузятся на `/zh-hans`, где ни один из них не покрывает основной текст (см. `02-i18n-geo.md`, §2.3).

## 6.5. Заголовков безопасности не хватает одного, зато важного

| Заголовок | Статус |
|---|---|
| `Strict-Transport-Security: max-age=63072000; includeSubDomains; preload` | ✅ |
| `X-Frame-Options: DENY` | ✅ |
| `X-Content-Type-Options: nosniff` | ✅ |
| `Referrer-Policy: strict-origin-when-cross-origin` | ✅ |
| `Permissions-Policy: camera=(), microphone=(), geolocation=()` | ✅ |
| **`Content-Security-Policy`** | ❌ **отсутствует** |
| `Cross-Origin-Opener-Policy` / `Resource-Policy` | ❌ |

CSP нет ни в каком виде. Для сайта, который планирует подключать GA4 и потенциально другие сторонние скрипты, это надо закрыть до подключения, а не после.

Дополнительно: HTML отдаётся с `Access-Control-Allow-Origin: *`. Для публичных статических страниц не опасно, но заголовок здесь ни к чему — стоит ограничить его `/api/`, если он вообще нужен.

`/api/submit` отвечает `405` на `GET` — корректно, ручка закрыта на метод. Признаков rate limiting по заголовкам не видно (проверялось только чтением, форму не отправляли).

## 6.6. Доступность: заметно выше среднего

**Сделано:**
- `Skip to main content` первой ссылкой;
- один `<h1>` на страницу, иерархия H2/H3 без пропусков (проверено на 4 страницах);
- `alt` у всех 13 изображений главной, осмысленные;
- форма: `<label for>` везде, `autocomplete`, `aria-describedby` у счётчика символов;
- чипы-мультивыбор: `role="group"` + `aria-labelledby` + `aria-pressed` — правильный паттерн для toggle-кнопок;
- honeypot в `aria-hidden="true"` с `tabindex="-1"`;
- слайдер: `<input type="range">` с `aria-valuetext="35 employees"` — нативный элемент, а не div;
- `prefers-reduced-motion` обработан во всех трёх CSS-файлах.

**Не проверено:** контрастность, фокус-кольца, поведение с клавиатуры, работа аккордеонов FAQ и «Show details» — для этого нужен рендер, а расширение Chrome в этой сессии не подключилось. Рекомендую прогнать axe DevTools / Lighthouse a11y вручную.

**Найдено по коду:**
- **тёмной темы нет** — `prefers-color-scheme` не встречается ни в одном из трёх CSS-чанков (0 вхождений), `theme-color` захардкожен `#2551D2`. Не дефект, но для B2B-аудитории в 2026 ожидаемо;
- у `<input type="range">` нет `aria-label`, только `<label for>` с текстом «Estimate by team size» — формально достаточно, но озвучка получится неполной («Оценка по размеру команды, 35 employees»), стоит добавить `aria-label` с полной формулировкой.

## 6.7. Юридические страницы написаны как внутренняя задача

**Слово «MVP» встречается 7 раз** в публичных юридических документах:

> «We do not purchase consumer data for **the MVP website**.»
> «**The MVP website** does not use personal information for cross-context behavioral advertising.»
> «Advertising personalization and Google Signals **must remain disabled for the MVP** unless the policy and consent flow are updated first.»
> «Consented analytics data **must be configured** with a maximum event-data retention period of 14 months **for the MVP**.»
> «**The MVP configuration must not send** form content, names, email addresses, company names, or free-form challenge text to analytics.»
> «The consent banner **must provide** equally accessible options to accept or decline optional analytics.»

Это не политика — это тикет в трекере, опубликованный на домене. Модальность «must» в юридическом документе адресована не пользователю, а разработчику. Для компании, которая продаёт операционную дисциплину, это самый разрушительный текст на сайте: он сообщает посетителю, что сайт — прототип, и что у самой компании процессы не доведены.

**Остальные проблемы юридического блока:**

1. **GDPR не упомянут ни разу.** Ни правового основания обработки, ни прав субъекта данных по ст. 15–22, ни механизма трансграничной передачи, ни представителя в ЕС. При этом сайт публикует четыре локали, собирает IP и «approximate location derived from IP address». Любая заявка от посетителя из ЕС/Великобритании — и политика не покрывает обработку.
2. **CCPA описан условно:** «If the California Consumer Privacy Act and California Privacy Rights Act **apply to Fill System**…». Компания не знает, применяется ли к ней закон её собственного штата. Для клиента, покупающего аудит рисков, это читается однозначно.
3. **Канал запросов субъекта данных — маркетинговая форма.** Дословно:
   > «To submit a privacy request, use the website diagnostic request form and begin the Main Challenge field with **Privacy Request**.»

   То есть чтобы удалить свои данные, нужно заполнить лид-форму, указать имя, рабочую почту и компанию (все три обязательны) и написать в поле «главная операционная проблема» кодовое слово. Это не рабочий DSAR-механизм. Адрес `privacy@fillsystem.com` в разделе «Contact» есть — но раздел «Your Choices» отправляет в форму.
4. **Юрлица нет.** «Fill System» — торговое имя. Ни LLC, ни Inc., ни номера регистрации, ни адреса. Идентификация контролёра данных отсутствует полностью.
5. **Cookie Policy без таблицы куки.** Нет ни одного имени куки, провайдера, назначения и срока. Вместо этого: «Actual cookies depend on the deployed configuration». Фактически сайт ставит одну куку — `NEXT_LOCALE` — и хранит согласие в `localStorage`; это можно было просто перечислить.
6. **Политика описывает несуществующую реальность.** «Google Analytics 4 may load only after you accept analytics cookies» — GA4 не загрузится никогда (см. §6.1). Формально не нарушение (обещано меньше, чем не делается), но документ и код рассинхронизированы.
7. **Дата «Last updated · June 13, 2026»** при последней публикации на сайте 29 июля 2026.
8. **Локализованные юридические страницы существуют** (`/ru/privacy-policy` отдаёт 200), но не включены в sitemap.

**Что делать:**
1. Вычистить все 7 вхождений «MVP» и всю модальность «must ... unless the policy is updated» — переписать в изъявительном наклонении от лица компании.
2. Добавить блок GDPR/UK GDPR: правовое основание, права субъекта, срок ответа, механизм передачи (SCC), контакт.
3. Убрать условность из CCPA-раздела — определить, применяется ли закон, и написать однозначно.
4. Сделать DSAR-канал: `privacy@fillsystem.com` как единственный маршрут во всех разделах, либо отдельная форма без обязательных маркетинговых полей.
5. Указать юрлицо и регистрационный адрес.
6. Добавить в Cookie Policy таблицу: `NEXT_LOCALE` (назначение, срок), запись согласия в localStorage, и GA4-куки — но только после реального включения аналитики.
7. Синхронизировать «Last updated» и добавить локализованные версии в sitemap.
